How it works

Four commands. Everything runs on your machine. No account, no telemetry, no cloud.

1saferoom init

Scans your .env* files and writes a dummy-credential template plus a tiny config. Real values are never copied.

2saferoom run

Clones the repo into a throwaway Docker container with the dummies mounted as .env. Point your agent at it — or pass the agent command directly. --offline cuts the network entirely.

3saferoom review

An audit report with the submitted one-shot entrypoint or interactive shell history, captured stdout/stderr, changed-file list, and full reviewable git diff.

4saferoom approve

Git-applies only the reviewed patch to your working tree. .env* files are hard-excluded, even if the agent edited them.

# an agent "cleans up" the billing schema inside the sandbox…
$ saferoom run --offline -- 'psql "$DATABASE_URL" -c "DROP TABLE customers;"'
[saferoom] session 20260821-201128 — cloning repo into sandbox
[saferoom] credentials swapped: .env (dummy .env mounted)
[saferoom] starting container saferoom-20260821-201128 (python:3.12-slim, offline)
psql: could not connect   ← DATABASE_URL was http://saferoom-stub.local; prod never heard about it

$ saferoom review
# SafeRoom audit — session 20260821-201128
- Isolation: docker (network: none)
- Credentials swapped: .env
## Submitted one-shot entrypoint
psql "$DATABASE_URL" -c "DROP TABLE customers;"
## Files changed
A   migrations/001_cleanup.sql
## Full diff
+DROP TABLE customers;
# your call. `saferoom approve` applies it — or you don't.

Why

Nearly half of AI-generated code fails security tests (Veracode, 2025). Claude Code and Cursor can refactor your whole backend from one prompt — and one hallucinated migration can drop your production tables. Every "the agent wrecked prod" story has the same shape:

The agent had real credentials

SafeRoom swaps every .env value for a generated dummy before the clone is mounted. The real values never enter the container.

The agent had a live target

The sandbox is a throwaway clone. Add --offline and the container has no network at all. Your working tree is untouched until you approve.

The human reviewed the damage, not the diff

SafeRoom flips the order: captured transcript + diff first, then a required sign-off. The review is the product, not an afterthought.

Guarantees

  • Real credential values never enter the container — only generated dummies do.
  • approve never writes .env* back, even if the agent edited them.
  • Throwaway clone — your working tree is untouched until approval.
  • Everything is local. No telemetry, no account, no cloud.
  • One readable file. Stdlib-only Python 3.8+. If you can read saferoom.py in one sitting — and you can — you know exactly what runs on your machine.
  • Works with what you already use. E2B, Modal, Daytona, Claude Code's /sandbox, Cursor — SafeRoom is the sign-off layer above them, not a replacement.

Install

Linux (Debian/Ubuntu) first. macOS: install Docker Desktop, then run the installer.

# Debian / Ubuntu
sudo apt-get update && sudo apt-get install -y git python3 docker.io
git clone https://github.com/kascadeceo/saferoom && cd saferoom
sudo ./install.sh

# then, in any project
cd your-project
saferoom init                  # dummy-credential template + config
saferoom run                   # interactive sandbox shell — point your agent here
saferoom run -- claude -p "refactor the billing module"   # or one-shot
saferoom review                # entrypoint/history, transcript, files, full diff
saferoom approve               # apply the reviewed patch (.env* always excluded)

Single-file Python, stdlib only. Read saferoom.py before you run it — that's the point.

FAQ

Why not just use git branches?

Branches don't stop an agent from reading your .env and hitting prod APIs during the run. SafeRoom's point isn't the diff — it's that the run itself happens against dummies, offline if you want, and the diff is the only thing that can come back.

Docker isn't a security boundary.

Agreed, for hostile code — that's what gVisor and Firecracker platforms are for. The threat model here is a well-intentioned agent making a catastrophic mistake with your credentials and your prod, not a jailbroken model escaping a kernel. For hostile-code isolation, run SafeRoom on top of a microVM.

Claude Code already has /sandbox. Cursor has sandbox mode.

They do, and they're good. They contain what the agent can touch while it's running. They don't strip your credentials from the clone, produce a standalone audit artifact, or gate application of the result. Different layer — use both.

Do I need Pro?

No. The complete local safety workflow — credential stripping, Docker isolation, entrypoint or interactive-history evidence, captured transcripts, full diffs, offline mode, and manual approval — is part of the free MIT-licensed CLI. Pro is planned for teams that need centralized history, policy enforcement, access controls, and evidence exports.

Does Pro make us compliant?

No tool makes an organization compliant on its own. Planned Pro evidence exports are intended to support your SOC 2, HIPAA, or EU AI Act review process; your controls, policies, implementation, and legal assessment still determine compliance.

What does it NOT catch yet?

The CLI records filesystem changes through git plus the submitted one-shot entrypoint and stdout/stderr transcript, or interactive shell history. It does not trace every child-process syscall. Database-mutation capture and API-call interception are roadmap items, not available today. --offline gives you --network none if you want the agent fully dark in the meantime.

Where do I report a security issue?

Don't open a public issue. Email security@kascadesecurity.com — you'll get a response within 48 hours. We especially want to hear where the credential-swap heuristics or the approve gate can be beaten.
